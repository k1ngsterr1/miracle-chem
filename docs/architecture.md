# Архитектура Miracle Chem

## Границы модулей

1. **Warehouse** — складские позиции, приходные партии, FEFO-расход, остатки, резервы, движения и история цен.
2. **Recipes** — независимые рецептуры с неизменяемыми версиями, датой действия и нормативными компонентами.
3. **Calculator / Formula Engine** — серверный расчёт состава, стоимости и дефицита; токенизация, parser, AST, Decimal-evaluator и пошаговая трассировка.
4. **Batches** — планирование замеса, резервирование, факт, завершение и корректировки.
5. **Product Lots** — выпуск, качество, прослеживаемость до использованных партий материалов.
6. **Shipments** — частичные отгрузки, приёмка, возвраты и идемпотентные движения; существующие таблицы `lrt_*` сохранены как технический контракт.
7. **Wagon Dislocation** — карточки вагонов и append-only события местоположения, статуса и груза.
8. **Expenses** — операционные затраты по категориям, центрам ответственности, способам оплаты и контрагентам.
9. **Reporting** — dashboard, производственный баланс, расходы, аналитические срезы, CSV/XLSX.
10. **Audit** — append-only журнал каждой критичной операции.

## Инварианты

- `Decimal` применяется на всех денежных и количественных полях; единица хранится рядом со значением.
- Значения разных физических измерений нельзя складывать или сравнивать.
- Масса ↔ объём пересчитывается только при заданной положительной плотности.
- Подтверждение расхода блокирует нужные складские строки и не допускает отрицательный остаток без явного override.
- Ручной расход использует только свободное количество FEFO-партий и не уменьшает резерв.
- Цена материала не перезаписывается без следа: текущая цена имеет запись в `MaterialPriceHistory`.
- Остаток готовой партии изменяется только через журнал движений продукта.
- Завершённый замес и его snapshots нельзя редактировать; исправление создаёт `AdjustmentDocument`.
- Повтор операции с тем же `idempotencyKey` возвращает прежний результат и не создаёт движение повторно.
- Расход нельзя физически удалить: отмена меняет статус, сохраняет причину и оставляет запись в истории/audit log.

## Состояния

Замес: `PLANNED → IN_PROGRESS → COMPLETED → PARTIALLY_TRANSFERRED → FULLY_TRANSFERRED`. В текущем API резервирование и подготовка выполняются атомарно при запуске; `PREPARATION` сохранён в модели для интеграции с внешним БСУ.

Альтернативные терминальные состояния: `CANCELLED`, `REJECTED`.

Отгрузка: `DRAFT → PREPARED → SENT → ACCEPTED | PARTIALLY_ACCEPTED | REJECTED`; до отправки возможна `CANCELLED`.

Вагон: `EMPTY | LOADING | LOADED | IN_TRANSIT | AT_DESTINATION | UNLOADING | RETURNING | MAINTENANCE`. Каждая смена состояния создаёт `WagonLocationEvent`.

Расход: `RECORDED → CANCELLED`. Отменённая сумма не входит в финансовые итоги, но доступна в журнале и отчёте.

## Транзакционные границы

- запуск замеса + резервирование материалов;
- подтверждение фактического расхода + списание/возврат резервов;
- ручной складской расход по нескольким FEFO-партиям;
- завершение замеса + создание партии готового продукта;
- отправка/возврат отгрузки + движение готового продукта;
- применение корректирующего документа.
- создание и отмена финансового расхода с защитой `Idempotency-Key`.

## Корректировки и неизменяемость

После `lockedAt` исходный замес не имеет update-маршрута. Исправление создаётся как `AdjustmentDocument`, получает snapshot `before`, причину и набор изменений, затем отдельно согласуется и применяется. Для материальных и продуктовых остатков применение создаёт ledger-движение `ADJUSTMENT`; для завершённого замеса и документа ЛРТ корректировка остаётся audit-overlay и не переписывает первичный документ.

## Безопасность эксплуатации

- в `production` по умолчанию включён `trusted-gateway`; без корректного server-side ключа и identity headers бизнес-API возвращает `401/503`;
- `/health` остаётся публичным для оркестратора;
- Fastify ограничивает body до 1 MiB, включает security headers и rate limit;
- `IdempotencyRecord` связывает ключ, scope и hash тела: повтор с другим payload возвращает конфликт;
- секреты и PostgreSQL не входят в образы и передаются только через окружение;
- бинарные вложения хранятся внешним object storage, API сохраняет проверенную связь и metadata.

## Отчётные срезы

Backend строит детализацию выпуска и склада, баланс партий, эффективность версий рецептур, журнал отгрузок, операционные расходы и trace конкретной партии. Производство агрегируется по смене, дню, ISO-неделе, месяцу, марке, линии и оператору; баланс — по партии продукта, замесу, марке, линии и ответственному. Каждый отчёт принимает произвольный период и экспортируется в CSV или OOXML/XLSX.
