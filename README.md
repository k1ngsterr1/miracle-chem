# Miracle Chem

Отдельная CRM для планирования, учёта и полной прослеживаемости производства бетона: от складской партии и версии рецептуры до замеса, готовой продукции, отгрузки, дислокации вагонов, расходов и первичных бухгалтерских документов.

## Архитектура

- `apps/web` — React CRM-интерфейс и аналитика.
- `apps/api` — NestJS API на стандартном Express-адаптере, транзакционные производственные операции и экспорт.
- `apps/one-c-sync-agent` — Windows-агент: принимает дельты от локальной 1С на loopback, сохраняет очередь и отправляет её в CRM по HTTPS.
- `packages/domain` — Decimal-расчёты, единицы измерения и безопасный движок формул.
- PostgreSQL + Prisma — основное хранилище; количество и деньги не используют `float`.

## Локальный запуск

```bash
cp .env.example .env
docker compose up -d postgres
npm install
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

Web: `http://localhost:5173` · API: `http://localhost:4100/api` · health: `http://localhost:4100/health`.

## Исторические Excel-отчёты

Два исходных отчёта за июль–август и сентябрь 2026 можно загрузить без изменения текущих остатков и документов 1С. Экстрактор сохраняет все заполненные ячейки, вычисленные значения и формулы, а также выделяет выпуск, расход, составы и однозначно подписанную реализацию. Сначала установите зафиксированную Python-зависимость в отдельное окружение (`python3 -m pip install -r scripts/historical-workbook-requirements.txt`), затем для каждого файла:

```bash
python3 scripts/extract-historical-workbook.py "/путь/Отчет 2026 Сентябрь.xlsx" > /защищённый/путь/september.json
npm run db:import-historical-workbook -- WORKSPACE_UUID /защищённый/путь/september.json "/путь/Отчет 2026 Сентябрь.xlsx"
```

Для второго файла используйте имя `Отчет 2026 июль-август.xlsx`. Импорт сверяет SHA-256 с оригиналом и при повторном запуске не создаёт дублей. При исправлении исходного файла прежняя версия сохраняется неактивной. Исходные файлы и извлечённый JSON содержат коммерческие сведения: не добавляйте их в Git и ограничьте доступ к временным файлам. В CRM выпуск без совпадающих дат 1С виден в общем журнале; при пересечении дат журнал отдаёт приоритет 1С, а исходная Excel-запись остаётся в «Отчёты → Исторические отчёты» для администратора, директора и бухгалтера. Там же доступны все листы и неоднозначные показатели. Архивный выпуск не участвует в текущих остатках, дебиторке и суммарных оборотах 1С до сверки первичных документов.

В production-контейнере `tsx` не устанавливается. После сборки передайте JSON и оригинал в защищённый временный каталог контейнера и запустите `node apps/api/dist/prisma/import-historical-workbook.js WORKSPACE_UUID /tmp/september.json '/tmp/Отчет 2026 Сентябрь.xlsx'` через `docker compose -f compose.production.yaml exec -T api`. Команда требует три аргумента и не создаёт рабочее пространство автоматически.

## Production-контур

`compose.production.yaml` собирает отдельные API и web-образы, однократно выполняет `prisma migrate deploy` через отдельный контейнер, включает HTTPS-прокси Caddy, healthcheck, security headers, rate limit, постоянное хранилище вложений и ежедневный бэкап PostgreSQL. Перед запуском задайте `POSTGRES_USER`, `POSTGRES_PASSWORD`, `AUTH_SESSION_SECRET` (32+ случайных символа), `ONE_C_SYNC_API_KEY`, `ONE_C_ARCHIVE_ENCRYPTION_KEY`, `ONE_C_SYNC_WORKSPACE_ID`, `ONE_C_SYNC_SOURCE_INSTANCE_ID`, `ONE_C_SYNC_ORGANIZATION_ID`, `CRM_DOMAIN`, `API_DOMAIN` и `WEB_ORIGIN=https://<CRM_DOMAIN>`.

На чистом VPS root может создать случайные секреты через `deploy/bootstrap-vps.sh`, передав два домена (`MIRACLE_CRM_DOMAIN`, `MIRACLE_API_DOMAIN`) и три **уже утверждённых** GUID привязки 1С (`ONE_C_SYNC_WORKSPACE_ID`, `ONE_C_SYNC_SOURCE_INSTANCE_ID`, `ONE_C_SYNC_ORGANIZATION_ID`) в окружении. Скрипт проверяет GUID и откажется перезаписывать существующий `.env` или начальный пароль администратора. Не генерируйте новые GUID вместо согласованного mapping. После первого применения миграций выполните seed **один раз** с `DEFAULT_ADMIN_PASSWORD` из `.admin-initial-password`; повторный seed сбрасывает пароль администратора.

Для уже развёрнутого VPS сначала передайте те же три утверждённых GUID и запустите `bash deploy/upgrade-one-c-env.sh`: скрипт дополнит существующий `.env` только недостающими переменными 1С, создаст ключ архива при необходимости и сохранит резервную копию исходного файла. При несовпадении существующего GUID он остановится без изменений; не заменяйте привязку автоматически.

```bash
docker compose -f compose.production.yaml up -d --build
```

Production API работает в `session`-режиме: пароль проверяется API, а браузер получает подписанную `HttpOnly; Secure`-сессию. Поэтому CRM должна открываться по HTTPS, а DNS обоих доменов — указывать на сервер. Секрет сессии должен быть уникальным и передаваться только через окружение сервера. Режим `trusted-gateway` оставлен для отдельной корпоративной интеграции, но не нужен для штатной страницы входа CRM.

Чеки и вложения сохраняются в отдельном постоянном томе `betonflow_storage`; ежедневные дампы PostgreSQL и архивы вложений хранятся 30 дней в `betonflow_backups`. Эти копии всё ещё находятся на том же VPS: для защиты от потери сервера необходима внешняя зашифрованная копия и периодическая проверка восстановления. Для рабочего контура с несколькими серверами хранилище следует заменить на S3/MinIO или корпоративное файловое хранилище.

Проверка и восстановление резервной копии:

```bash
docker compose -f compose.production.yaml exec backup ls -lh /backups
docker compose -f compose.production.yaml exec -T backup sh -c 'cat /backups/miracle-chem-YYYYMMDDTHHMMSSZ.dump' | docker compose -f compose.production.yaml exec -T postgres pg_restore --clean --if-exists --username "$POSTGRES_USER" --dbname "$POSTGRES_DB"
```

## Гарантии домена

- формулы разбираются парсером и исполняются по AST, без `eval`;
- единицы всегда приводятся к совместимому базовому измерению;
- завершённый замес хранит immutable snapshot рецептуры, формул, цен и фактических значений;
- резервы, списания, выпуск партии и отгрузка выполняются транзакционно;
- ручной складской расход списывается по FEFO и не затрагивает резерв замесов;
- складские движения и отгрузки защищены `idempotencyKey`;
- каждая закупочная цена и отметка дислокации сохраняются отдельной строкой истории;
- финансовые расходы создаются идемпотентно, а отмена сохраняет исходную запись и исключает её из итогов;
- суммы позиций, НДС и итог бухгалтерского документа рассчитываются на сервере; выставление, оплата и отмена записываются в audit log;
- корректировки оформляются отдельными документами и попадают в audit log.

## Основные API-контуры

- `/api/materials`, `/api/materials/receipts`, `/api/materials/consumptions` — склад, партии, приход, расход и история цен;
- `/api/recipes`, `/api/formulas` — версии рецептур и безопасные серверные формулы;
- `/api/calculator/recipe` — расчёт состава, стоимости и складского дефицита;
- `/api/batches` — план, резервирование, факт, завершение и отмена;
- `/api/product-lots` — партии продукта, списания, брак и другие отгрузки;
- `/api/transfers` — внутренний API документов отгрузки, приёмки, возврата и отмены;
- `/api/wagons` — вагоны и append-only история дислокации;
- `/api/expenses` — операционные расходы, категории, центры затрат, способы оплаты и отмена;
- `/api/accounting` — накладные, счета на оплату, акты выполненных работ и их жизненный цикл;
- `/api/adjustments` — отдельное согласование и применение корректировок;
- `/api/attachments` — привязка сертификатов и документов;
- `/api/integrations/1c` — идемпотентный обмен изменениями с офлайн 1С и ручная проверка спорной номенклатуры;
- `/api/reports` — выпуск, расход сырья, финансовые расходы, баланс, эффективность рецептур, отгрузки, CSV/XLSX и trace партии.
